# Interview a New Site's Owner: the Question Bank

The reference behind `site/.agents/skills/interview-the-owner-of-a-new-site.md`. It holds every question
that only the owner of a new site can answer, in the order the answers are needed. Each question says
where the answer lands, what breaks when it is wrong, and which earlier questions it needs. Where a real
choice exists, the options come with their trade-offs and a recommendation.

`scripts/check-engine.mjs` points here when the engine is copied into an empty repository and its
self-check has findings. It also reads this file. `npm run gate:engine` fails with `ENGINE interview-gap <name>`
when a leaf value of `site/engine.config.json`, a secret or a variable that a workflow reads, or a variable
that `site/.env.example` names, is not written here as a whole word. Add a new one to the question that sets
it, and to the table of config values in Part 1 or to the secret and variable tables in Part 3.

## How to use it

- Ask one question at a time. Give the recommended answer. Never ask what the repository already says.
- Run Part 1, then Part 2, then Part 3. Inside a part, follow the order list at its head.
- Write each answer where its `Lands in` line says. Do not keep a separate note.
- A claim marked `[INFERENCE]` was not checked against code. Check it before you rely on it.
- Citations of the form `path:line` were read at the time of writing. The line may have moved.

## The three parts

1. The site: scope and layout, identity, pages and navigation, the loop policy, Search Console demand,
   hosting and the performance bar. Question ids `S1` to `S48`.
2. The semantic core: the business, the buyer, what the owner can prove, families, buyer prompts,
   words, categories and tags, and the contract a complete core must meet. Ids `K1` to `K34`.
3. The platform: the secrets and the repository settings with what fails when each is absent, the
   failures that already happened, and the decisions around them. Ids `P1` to `P15`.

## Part 1. The site, its pages and its loop

This part collects what only the owner can say about the new site, apart from the semantic core and the secrets. Ask one question at a time. Give the recommended option first. Never fill an owner fact from a guess. Every answer lands in a named file or key, and every "If wrong" line names the check that shows the mistake.

### Order and dependencies

1. Phase 1 (S1 to S6) fixes scope and layout. S2 needs S1. Every later phase depends on it.
2. Phase 2 (S7 to S19) is identity. S8 needs S3 and S7. S12 needs S11. S13 needs S11 and S12. S15 needs S7. S16 needs S3 and S7. S17 needs S4. S19 needs S7 and S18.
3. Phase 3 (S20 to S29) is pages, hubs and navigation. S21 needs S20. S26 needs S22. S29 needs S15, S20 and S21.
4. Phase 4 (S30 to S35) is the loop policy. It needs S2. S33 needs S30. S34 needs S32.
5. Phase 5 (S36 to S40) is Search Console demand. It needs S1 and S7.
6. Phase 6 (S41 to S46) is hosting. It needs S3. S43 needs S7, S8 and S41. S46 needs S43.
7. Phase 7 (S47 and S48) is the performance bar. S47 needs S5. S48 needs S18.
8. Other parts own the semantic core (buyer prompts, categories, tags, the business reason of each family), the secret values and the repository settings. This part asks only the names and policies they need.

### Phase 1. Scope and layout

The site shell and the harness are always adopted. They are the Astro app, the gates, the self-check `npm run gate:engine` and the skills. These six questions decide which optional modules run.

#### S1. Search Console demand loop

**Ask:** Do you want the site to pick topics from real Search Console data? It needs a Google service account that can read your Search Console property.
**Cannot be derived because:** Only the owner can create and control a Google account, and only the owner decides whether to connect it.
**Options:**

- **A. Adopt:** `npm run audit:demand` writes `audits/search-demand.md` from Search Console, and `gate:demand` keeps it fresh. Cost: one secret (`GSC_SERVICE_ACCOUNT_JSON`, a service-account key that the property lists with Restricted permission), one Google Cloud project with the Search Console API enabled, no money [INFERENCE: nothing in the repository bills for the API], and upkeep: the report must stay younger than `demand.maxAgeDays` or CI goes red.
- **B. Skip:** pick topics by hand from the buyer prompts. Cost: the unattended writer cannot run (S2), you remove `gate:demand` from `ci.yml` and the anchor `audits/search-demand.md` from `site/scripts/engine-anchors.mjs`, and you lose the strengthen reports that point at pages already ranking.
- **Recommended:** A, because the report is the only evidence the engine has that a topic is wanted and it costs no money, unless you cannot create a Google Cloud service account.
  **Lands in:** repository secret `GSC_SERVICE_ACCOUNT_JSON`; the report `audits/search-demand.md`; the values set in S36 to S40.
  **If wrong:** With no key, `npm run audit:demand` exits 3 with `GSC_SERVICE_ACCOUNT_JSON is not set. Put the whole service-account JSON on one line in <the file or secret that holds it>`. With a key the property does not list, it exits 3 with `Search Console refused the property <property> for the service account`. A kept gate with a missing or old report fails CI with `DEMAND report-stale audits/search-demand.md: measured <date>; refresh with npm run audit:demand (<n> days old, limit <max>)`, or with `no "Measured: YYYY-MM-DD" line with a real date, so its age cannot be shown` when the report has no date line.
  **Needs:** none

#### S2. Unattended writer

**Ask:** Do you want a machine to write one article a day, open a pull request, wait, and merge it if every check is green?
**Cannot be derived because:** Only the owner can accept the model spend, the accounts and the review duty.
**Options:**

- **A. Adopt:** the workflows `write-daily.yml` and `watch-pr.yml` run. Cost: four secrets (`AUTOWRITER_PAT`, a token of a bot GitHub account; `AUTOWRITER_OPENAI_API_KEY`; `GSC_SERVICE_ACCOUNT_JSON`; `SLACK_WEBHOOK_URL`), four variables (`WRITING_PROVIDER`, `OPENAI_WRITING_MODEL`, `OPENAI_WRITING_INPUT_USD_PER_MILLION`, `OPENAI_WRITING_OUTPUT_USD_PER_MILLION`), an environment `autowriter-tick` with a wait timer, and model spend up to the ceiling in S33. The vendor is fixed: one adapter, `site/scripts/writer-adapter.mjs`, calls OpenAI (locked row L63). Upkeep: read escalation issues and Slack posts, look at each pull request before it merges, and clear the measurement debt each merge leaves with `npm run gate:lh` then `npm run lh:record`.
- **B. Install, do not configure:** keep the files and set none of the names. Cost: nothing. The daily run reports green and writes nothing.
- **C. Remove:** delete both workflows and the writer scripts. Cost: code edits in `ci.yml`, `package.json` and `site/scripts/engine-anchors.mjs`, with `gate:plan` and `gate:engine` as the judges.
- **Recommended:** B until the semantic core and the first hand-checked entries pass every gate, then A, because the writer prompt quotes `AGENTS.md`, `docs/SEMANTIC-CORE.md` and `docs/CONTENT-GATE.md` and is only as good as they are, unless you want daily articles from day one. Under B nothing refreshes `audits/search-demand.md`, so run `npm run audit:demand` by hand and commit the report inside the age limit of S38.
  **Lands in:** repository secrets and variables named above; `.github/workflows/write-daily.yml`; `.github/workflows/watch-pr.yml`; the `loop` section of `site/engine.config.json` (S31 to S35).
  **If wrong:** With any name missing, the daily run ends green and its summary reads `The unattended writer is not configured yet` followed by `The repository is missing:` and the names. A Search Console credential that Google refuses raises a `credential` escalation, which opens an issue and posts to Slack.
  **Needs:** S1

#### S3. Cloudflare Pages publishing

**Ask:** Do you want the site published on Cloudflare Pages from the build that the gates measured?
**Cannot be derived because:** Only the owner holds the Cloudflare account and chooses the host.
**Options:**

- **A. Adopt:** `npm run deploy` uploads the gated `dist/` with wrangler, and the Publish Live workflow does it on request. Cost: one secret (`CLOUDFLARE_API_TOKEN`, scopes Account > Cloudflare Pages > Edit and User > User Details > Read), two variables (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_PAGES_PROJECT`), no hosting money (the engine rule L58 says the domain is the only thing bought), and upkeep: someone presses Publish Live for each release, and a gated build stays publishable for 14 days (`retention-days` in `ci.yml`).
- **B. Host elsewhere:** Cost: you rewrite `dist/_headers` (`site/scripts/gen-headers.mjs`), the edge handler `dist/_worker.js` that answers `Accept: text/markdown`, the deploy scripts and `publish-live.yml`.
- **Recommended:** A, because headers, the edge handler and the smoke test all assume Pages, unless the site must live on another host.
  **Lands in:** your local copy of `site/.env.example` (named `.env`) and the repository variables and secret above; `.github/workflows/publish-live.yml`; `site/scripts/deploy.mjs`.
  **If wrong:** Without the names, `npm run deploy:check` prints `DEPLOY CLOUDFLARE_API_TOKEN is not set; site/.env.example names it and the token scope it needs`. The `deploy-preview` job of `ci.yml` is a required job, so every code pull request stays red with the same `DEPLOY` line. Under B, `npm run gate:agents` refuses a build with no `_worker.js`.
  **Needs:** none

#### S4. Machine and agent interfaces

**Ask:** Do you want the site to publish files for AI agents and feeds: `llms.txt`, Markdown copies of pages, feeds, an OpenAPI document, the catalogs, and Markdown on request?
**Cannot be derived because:** The owner decides whether agents and answer engines should find and quote the site.
**Options:**

- **A. Adopt:** the build writes the files and `npm run gate:agents` checks them. Cost: no secret, no money. Upkeep: keep the gate green, and check the two Cloudflare zone switches in S43. One edge handler exists, `site/scripts/markdown-negotiation.mjs`, copied to `dist/_worker.js`.
- **B. Skip:** remove the generators and the gate. Cost: code edits in `package.json` and `ci.yml`, and you drop the `smoke:prod` rows for `/llms.txt`, `/rss.xml`, `/feed.json` and the Markdown negotiation row [INFERENCE: dropping needs these edits together, and `gate:plan` flags leftovers].
- **Recommended:** A, because the files are derived from the build and cost nothing to keep, unless you want no machine-readable surface at all.
  **Lands in:** `site/scripts/gen-robots.mjs`, `site/scripts/gen-headers.mjs`, `site/scripts/gen-openapi.mjs`, `site/scripts/gen-agent-catalog.mjs`, `.github/workflows/ci.yml`.
  **If wrong:** `npm run gate:agents` prints findings such as `_headers: no response declares a Content-Signal` or fails a build with no `_worker.js`. `npm run smoke:prod` prints `FAIL route /llms.txt: answered 404, expected 200`.
  **Needs:** none

#### S5. Local Lighthouse gate

**Ask:** Will you run Lighthouse on your own machine before each code push, and accept that a push of an unmeasured tree is refused?
**Cannot be derived because:** The owner must give a quiet machine and about 30 minutes per measured change.
**Options:**

- **A. Adopt:** `npm run gate:lh` measures every audited route on mobile and desktop, `npm run lh:record` writes the Lighthouse record, and `.githooks/pre-push` refuses a push whose tree no record measured. Cost: no secret, no money, about 30 minutes per run on a quiet machine, and the hook installed once (`git config core.hooksPath .githooks`). Each unattended merge (S2) leaves a measurement debt that this run clears.
- **B. Skip:** remove the hook, the gate and the Lighthouse hard rule in `AGENTS.md`. Cost: you lose the only proof that the pages score 100 in every category.
- **Recommended:** A, because the engine has no waiver path and CI does not run Lighthouse, unless the machine that pushes cannot sit idle for 30 minutes.
  **Lands in:** `.githooks/pre-push`; `site/lighthouserc.cjs`; the Lighthouse record (written by the run).
  **If wrong:** `.githooks/pre-push` runs `node site/scripts/run-lh-evidence.mjs check` and refuses the push with the reason that `staleReason` in `site/scripts/lh-evidence.mjs` returns [INFERENCE: the wording was not read]; a covered tree prints `lighthouse evidence covers this tree (<12 hex characters>)`. A prose-only commit pushes freely. `npm run lh:record` refuses with `<files> is not committed, so a fingerprint of HEAD would name a tree the run never measured. Commit, rebuild, measure, then record.` `npm run gate:lh` without `GATE_PHASE` fails at once with `gate:lh: GATE_PHASE must name the bucket these audits belong to` and an example value.
  **Needs:** none

#### S6. Repository layout

**Ask:** Do you keep the engine's layout: the Astro app in `site/`, and `docs/`, `audits/`, `openspec/`, `investigation/` and `.github/` at the repository root?
**Cannot be derived because:** The agent cannot know whether you plan another package or layout in the same repository.
**Options:**

- **A. Keep:** the `diff` section and `content.dataDirectory` stay as they are. Cost: none.
- **B. Move the app to the repository root:** Cost: you change every `site/` path in the `diff` section, in `site/scripts/engine-anchors.mjs`, in the workflows (`working-directory: site`) and in `.githooks/pre-push`, and the scripts that read `docs/` and `audits/` through the parent of `site/` change too.
- **Recommended:** A, because the classifier that picks the CI graph reads these paths from one file and the rest of the engine assumes them, unless a tool forces another layout.
  **Lands in:** `site/engine.config.json`, keys `diff.proseDirectories`, `diff.proseExtensions`, `diff.shippedDirectories`, `diff.automationDirectories`, `diff.testTooling`, `diff.testFilePattern`, `diff.testDirectoryPattern` and `content.dataDirectory`.
  **If wrong:** `npm run gate:engine` prints `ENGINE anchor-missing <path>: the <kind> is absent; it is <role>` for each moved file. Every config problem reads `ENGINE config-invalid <field>: <problem> in site/engine.config.json; <description>`. A data directory outside the shipped directories prints `ENGINE config-invalid content.dataDirectory: "<dir>" is not inside a diff.shippedDirectories entry, so the entries the writer commits would classify as prose and skip the gates in site/engine.config.json; <description>`. Two lists that overlap print `ENGINE config-invalid diff.<list>[<n>]: "<directory>" overlaps "<other>" in diff.<otherList>, so a path under both would have two classes in site/engine.config.json; <description>`.
  **Needs:** none

### Phase 2. Identity

#### S7. Apex domain and brand name

**Ask:** What is the apex domain of the site? Do you accept that the brand name is written exactly as that domain, for example `<apex>`?
**Cannot be derived because:** Only the owner knows which domain they own or will buy, and how they want the name written.
**Options:**

- **A. Brand name is the apex hostname:** one value, `site.name`. The engine builds the title suffix, the contact address `hello@<name>`, the bot address `autowriter-bot@<name>`, the IndexNow host and every machine-file URL from it. Cost: the brand reads as a domain in titles and footers.
- **B. A spaced display name:** Cost: a code change before the copy: `site/src/utils/brand.mjs` must hold a display name and a host as two values, and about ten scripts and four pages that read `site.name` as a host change with it.
- **Recommended:** A, because the engine treats the name as a host in `brand.mjs`, `gen-robots.mjs`, `indexnow-ping.mjs`, `pr-classify.mjs` and `run-smoke-prod.mjs`, unless the display name must contain spaces.
  **Lands in:** `site/src/config.yaml`, keys `site.name`, `site.site` and `metadata.openGraph.site_name`; typed copies in `humans.txt`, `security.txt` and `.github/workflows/ci.yml` (a typed bot address on a foreign domain in the `regen-baselines` job).
  **If wrong:** With a name that is not a host, `hello@<name>` and the bot address `autowriter-bot@<name>` are invalid, `node scripts/indexnow-ping.mjs` prints `indexnow: skipped (key-not-served)`, and `npm run smoke:prod` cannot reach its default origin `https://<name>` [INFERENCE: no run with a bad name]. `npm run gate:brand` prints `brand: <n> files scanned, <m> typed literals of the configured brand name` for code that types the name. YAML, `public/` and workflows are not scanned, so a typed copy there drifts without any message.
  **Needs:** none

#### S8. Canonical host and www policy

**Ask:** Which host is canonical, the apex or `www.<apex>`? What does the other host do?
**Cannot be derived because:** The owner may already have links, listings or a Search Console property on one form.
**Options:**

- **A. Apex canonical, `www` answers 301 to the apex with the path kept:** Cost: a proxied DNS record for `www` and a redirect rule in Cloudflare.
- **B. Apex canonical, no `www` record:** Cost: you delete the `www` block of `site/scripts/run-smoke-prod.mjs`, whose `www` requests I saw with no `try` around them [INFERENCE].
- **C. `www` canonical:** Cost: unsupported. Machine files build `https://<site.name>`, so the apex name is baked in [INFERENCE: it would need many script edits].
- **Recommended:** A, because `npm run smoke:prod` checks exactly this redirect on `/` and `/about`, unless the domain already ranks on `www`.
  **Lands in:** Cloudflare DNS and a redirect rule (outside the repository); `site/src/config.yaml` key `site.site`; `site/scripts/run-smoke-prod.mjs`.
  **If wrong:** `npm run smoke:prod` against the apex prints `FAIL www redirect /: answered 200, expected 301` or `301 to <location>, expected <origin>/`. A `www` host with no DNS record makes the request throw, and the run ends with a Node error and no report [INFERENCE: nothing catches it].
  **Needs:** S3, S7

#### S9. URL shape and trailing slash

**Ask:** Do you accept URLs without a trailing slash and without `.html`, such as `/about`?
**Cannot be derived because:** An existing domain may already have indexed URLs in another shape.
**Options:**

- **A. No trailing slash:** the build writes `about.html`, and the site serves `/about`. Cost: none, it is the shipped shape.
- **B. Trailing slash:** Cost: you change `trailingSlash` and `build.format` in `site/astro.config.ts`, `site.trailingSlash` in `site/src/config.yaml` and the `EXTENSIONLESS_LOCAL` pattern in `site/scripts/links-gate.mjs`; the route derivation in `site/scripts/gate.mjs` and the route ledger may also change [INFERENCE: not tried].
- **Recommended:** A, because the shape is set in two files and read by the link gate, the sitemap and the route ledger, unless the domain already has indexed URLs with slashes.
  **Lands in:** `site/astro.config.ts` (`trailingSlash: 'never'`, `build.format: 'file'`); `site/src/config.yaml` (`site.trailingSlash: false`).
  **If wrong:** Pages answer with a redirect instead of 200, so `npm run smoke:prod` prints `FAIL route /<page>: answered 301, expected 200` and the link checker reports broken internal links [INFERENCE: the redirect on a changed shape was not run].
  **Needs:** S7

#### S10. Language

**Ask:** In which language will the pages and articles be written?
**Cannot be derived because:** Only the owner knows the language the buyers search in.
**Options:**

- **A. English:** the shipped language. Cost: none.
- **B. Another language, for example Russian:** Cost: `i18n.language` and `textDirection` change, and the prose rules are English: `site/banned-phrases.json`, `site/controlled-words.json`, and in `site/scripts/topic-format.mjs` the word lists and patterns `SUBJECT_STOP_TOKENS`, `SUBJECT_BAD_FIRST_WORDS`, `DEFINITION_LEAD`, `PROCEDURAL_LEAD` and `QUESTION_WORDS`. The writer prompt and the sentence band `audits/sentence-band.json` need new calibration [INFERENCE].
- **Recommended:** A, because every prose gate and the topic picker were built and measured on English, unless the buyers do not search in English; then treat it as a separate adaptation project and do not start with copy.
  **Lands in:** `site/src/config.yaml` key `i18n.language`; `site/src/utils/jsonld.mjs` constant `LANGUAGE`; `security.txt` field `Preferred-Languages`.
  **If wrong:** Under B with English rules left in place, `npm run gate:content` and `npm run gate:human` judge words they do not know, so findings are noise or silence [INFERENCE]. The topic picker's cues are English words, so it finds no definition queries and writes no glossary terms [INFERENCE].
  **Needs:** none

#### S11. Entity: person, organisation, or both

**Ask:** Does the site speak as a person, as an organisation, or as a person who trades under a brand?
**Cannot be derived because:** Only the owner knows who is accountable for the advice and what they will sign.
**Options:**

- **A. Person who trades under a brand:** a `Person` node and an `Organization` node named as the brand, with the person as founder. Cost: the person's name appears on the site.
- **B. Organisation with one named author:** the same two nodes. Cost: you still name one person, because every article needs an author.
- **C. Organisation with a team byline:** Cost: the engine models only a person author, so this needs code changes in `jsonld.mjs` and the author schema.
- **Recommended:** A or B, because `site/src/content.config.ts` requires an `author` reference on every article and the law in `AGENTS.md` forbids invented credentials, unless the organisation cannot name a person.
  **Lands in:** `site/src/utils/jsonld.mjs`, constants `PERSON_NAME`, `PERSON_ROLE`, `PERSON_SAME_AS`, `ORG_SAME_AS` and `KNOWS_ABOUT`, which are typed in code and not read from the author file; `site/src/pages/about.astro`.
  **If wrong:** A node that references an `@id` no node defines fails `npm run gate:jsonld` (`AGENTS.md`: every referenced `@id` resolves). Typed constants that differ from the author entry give two names for one person, with no gate to compare them [INFERENCE: no comparison found].
  **Needs:** S7

#### S12. Author name, slug, role, bio and credentials

**Ask:** What are the author's name, a lowercase slug, a one-line role, a bio of one or two sentences, and any credentials you can prove?
**Cannot be derived because:** These are facts about a real person, and the engine never invents a name, a bio or a credential.
**Lands in:** `site/src/data/author/<slug>.md`, front matter `name`, `role`, `bio`, `sameAs` (at least one URL) and `credentials` (default empty); `site/engine.config.json` key `content.formats.article.author` (the slug).
**If wrong:** A slug that is not lower-case letters, digits and hyphens, or does not start with a letter, fails `npm run gate:engine` with `ENGINE config-invalid content.formats.article.author: must match pattern ^[a-z][a-z0-9-]*$ in site/engine.config.json; The slug of the author entry that every written article names.` A slug with no file under `site/src/data/author/` breaks the build when an article references it [INFERENCE: the content layer cannot resolve the reference]. An unproven credential breaks the law in `AGENTS.md` and fails review, not a gate.
**Needs:** S11

#### S13. Public profiles

**Ask:** Which public profiles represent you and the brand: LinkedIn, GitHub, others? Do they link back to the site?
**Cannot be derived because:** Only the owner knows which accounts exist and are theirs.
**Options:**

- **A. Person and organisation profiles:** Cost: you keep each URL current in four places.
- **B. Person profiles only:** Cost: the organisation node carries no `sameAs`.
- **Recommended:** A with only profiles that exist, because the author schema needs at least one URL and a profile that does not link back adds nothing, unless the brand has no profile yet.
  **Lands in:** `site/src/data/author/<slug>.md` (`sameAs`); `site/src/utils/jsonld.mjs` (`PERSON_SAME_AS`, `ORG_SAME_AS`); `site/src/navigation.ts` (`footerData.socialLinks`); `site/scripts/links-gate.mjs` (`THIRD_PARTY_HOSTS`, which holds a typed organisation path from the first site).
  **If wrong:** An author with no `sameAs` URL fails the build on the author schema, which needs at least one URL. The about page prints the author's `sameAs` links and credentials, so a wrong URL is public. A dead profile URL fails no gate: `npm run gate:links` never fetches an address outside the build, and a daily job repairs a dead citation (`site/.agents/skills/link-out.md`). A profile URL that is no address (whitespace, no parse, a host that is not a domain) prints `LINKS malformed <finding>` and exits 1.
  **Needs:** S11, S12

#### S14. Location policy

**Ask:** What may the site say about where you work: nothing, a region, or a full postal address?
**Cannot be derived because:** It is a privacy choice, and some jurisdictions require an address in the imprint [INFERENCE: this varies by country; get legal advice].
**Options:**

- **A. Remote, no address:** the imprint row reads as remote work. Cost: it may not satisfy a legal imprint duty.
- **B. City or region only:** Cost: the owner's town becomes public.
- **C. Full postal address:** Cost: the address becomes public and indexable.
- **Recommended:** A when the law allows it, because the engine's imprint template has no address row, unless your jurisdiction requires one; then C.
  **Lands in:** `site/src/pages/imprint.astro` (the working-from row); `humans.txt` (`Location`); the contact page text; `site/src/utils/jsonld.mjs` carries no address today.
  **If wrong:** No gate reads the location. A missing legal address shows only as a legal risk, not as a failing check.
  **Needs:** S11

#### S15. Contact route and the one next step

**Ask:** What is the one next step you want every page to offer, and which email address do readers use?
**Cannot be derived because:** Only the owner chooses how buyers reach them.
**Options:**

- **A. Booking link plus an email address:** one URL in `BOOKING_URL` and one label in `BOOKING_LABEL`, and `hello@<apex>` as the written route. Cost: the booking vendor sees the visitor on click; the link is outbound, so it carries `rel="nofollow noopener noreferrer"`.
- **B. Email address only:** set `BOOKING_URL` to a `mailto:` address [INFERENCE: the gate compares the href text, so this passes, but no run proved it]. Cost: the label and the near-miss help in the gate assume a calendar host.
- **C. Another action, such as a purchase or a download:** Cost: `site/scripts/booking-cta.mjs` and the header and footer data change.
- **Recommended:** A, because `AGENTS.md` allows no form, no mail sending and no newsletter, so a calendar page and an inbox are the supported routes, unless the owner does not take calls.
  **Lands in:** `site/src/utils/booking.mjs` (`BOOKING_URL`, `BOOKING_LABEL`, which hold the first site's values today); `site/src/utils/booking.test.mjs` and `site/tests/header.spec.ts`, which pin the first site's booking host (the unit test also its path) and must be rewritten with it; `site/scripts/links-gate.mjs` (`THIRD_PARTY_HOSTS`, which skips one typed booking host); `site/src/pages/contact.astro`; `site/src/navigation.ts` (the header action, whose text is typed there).
  **If wrong:** `npm run gate:content` prints `booking-cta-missing` on each indexable route with `no link to <url> inside <main>; header and footer do not count`. With the old test files left in place, `npm test` fails in `site/src/utils/booking.test.mjs` on its origin and path assertions, and the header spec selector matches no button [INFERENCE: I read the selector, not a run]. A booking address that is gone fails no gate: `npm run gate:links` never fetches an address outside the build, so only a booking address that is no address can fail it (`LINKS malformed <finding>`).
  **Needs:** S7

#### S16. Analytics

**Ask:** Do you want visitor counts? If yes, do you accept Cloudflare Web Analytics, which sets no cookie?
**Cannot be derived because:** Only the owner decides what is measured about visitors, and the privacy page must say it.
**Options:**

- **A. Cloudflare Web Analytics:** set `site.analyticsSiteToken`. Cost: one third-party script, `static.cloudflareinsights.com`, allowed in the CSP only when the built HTML carries it; the imprint and privacy text must say pages are counted.

## Part 2. The semantic core and the buyer prompts

This part asks the owner of a new site for everything the source repository keeps in `docs/SEMANTIC-CORE.md` and the files around it: the business, the buyer, the proof, the terms, the families, the buyer prompts, the competitors, the words, the numbers, the categories and the tags. It has 34 questions in 7 phases. The agent asks one question at a time, gives the recommended answer, and writes the answer to the place named in **Lands in**. The agent never asks for a fact it can read from the repository. The last section, `## Contract of a complete core`, lists the structure the gates and parsers demand, with the line that enforces each item.

Line numbers point at the engine files in this repository. A claim marked [INFERENCE] was not confirmed in code.

### Order and dependencies

1. Phase 1, K1 to K6: the business and the buyer. K1 comes first because it decides whether the engine fits at all.
2. Phase 2, K7 to K12: what the owner can honestly prove. Needs K2.
3. Phase 3, K13 to K18: collections, terms and families. Needs K2, K3, K4 and K6.

7. Phase 7, K32 to K34: categories and tags. Needs K13 and K18.

### Staging

The core cannot be complete on day one. A `Must win` route must be built, and a `Passage` must be a literal sentence of a built page (`site/scripts/semantic-core.mjs:307`, `site/scripts/semantic-core.mjs:323`). Work in this order:

1. Ask K1 to K34 and write each answer to the file named in **Lands in**.
2. Create the seed pages and one `targetQuery` row per route (K2, K13, K33, K34).

**Cannot be derived because:** it is the owner's taste and brand voice.

#### K30. How the site sounds

### Phase 1. Whether the loop runs, and where

#### P1. Adopt unattended writing at all

**Ask:** Do you want a machine to write an article every day, open the pull request and merge it without you, or do you want only the gates, the previews and the manual publish button?
**Cannot be derived because:** it sets how much risk, money and daily attention you accept. The repository supports both.
**Options:**

- **A. Full loop:** `.github/workflows/write-daily.yml` writes, `.github/workflows/watch-pr.yml` judges and squash-merges into `main`. The watcher still merges only when every required job and the aggregate are green on the head (`site/.agents/skills/watch-an-unattended-pull-request.md:19-21`), so the loop itself stays covered. Row G48 of `docs/plan/reference/known-gaps.md` records this state and its cost in the source repository.
- **Recommended:** A, because a red pull request stays unmergeable by hand and the loop can still commit, unless the bot cannot join a bypass list without becoming a full administrator. Then C, with the watcher as the only gate.
  **Lands in:** a ruleset or branch protection on `main`, in GitHub settings. No engine file changes. The required name is the string in `.github/workflows/ci.yml:241`.
  **If wrong:** On B, the step `commit the refreshed report to main` exits 1 with `commit-to-main: <git message>` (`site/scripts/commit-to-main.mjs:196-197`). The run is red, no model is called, and no escalation fires [INFERENCE: no `failure()` step names that step, `.github/workflows/write-daily.yml:133-147`]. If you also turn on "require branches to be up to date", the watcher's merge is refused whenever the daily commits have moved `main` since the branch was cut. The runner returns `refused` and the watcher escalates `hard-stop` (`site/scripts/pr-github.mjs:143`). If you also require a human review, the bot's own pull request can never merge. If you also require signed commits, the bot's commits are refused [INFERENCE].
  **Needs:** P2, P3

#### P12. How long the watcher waits between looks

**Ask:** How many minutes should the watcher wait between looks at an article pull request?
**Cannot be derived because:** it trades reaction speed against the number of runs, and the balance depends on your plan, your CI time and how soon you want a merge once the quarantine ends.
**Options:**

- **A. The shipped default, 3 minutes:** `loop.tickMinutes` is 3 in `site/engine.config.json`, and the skill sets the environment's timer to 3 (`site/.agents/skills/watch-an-unattended-pull-request.md:56-57`). A quick merge after the quarantine and a fast reaction to a red CI. Cost: many runs for each pull request. The count is the quarantine in minutes (`loop.quarantineHours` times 60) divided by this wait. Each run is a job, and metered plans bill each job by the started minute [INFERENCE].
- **B. Medium, 10 minutes:** fewer runs. Cost: a merge can lag up to ten minutes behind the end of the quarantine, and a red CI is noticed up to ten minutes late. It was the value of the constant before commit `9984266` made it configuration.
- **C. Long, 30 minutes or more:** few runs. Cost: slow reaction, and the chain must still settle before its age limit, which the watcher reads as `no-convergence` (`site/.agents/skills/watch-an-unattended-pull-request.md:29-30`).
- **Recommended:** A, because the config, the code and the skill already use it and no test or doc needs changing, unless the repository is private on Enterprise with metered minutes. Then B or C.
  **Lands in:** the environment `autowriter-tick` (its wait timer) and `loop.tickMinutes` in `site/engine.config.json`, which `site/scripts/pr-watch.mjs:28` reads. The two numbers must agree: the environment must wait at least as long as the code expects (`site/scripts/pr-github.mjs:185`). Raise the environment first and the code second. Lower the code first and the environment second.
  **If wrong:** The environment waits fewer minutes than the code expects: the Watch PR run ends red with `The environment autowriter-tick waits <n> minutes, less than the <m> the tick needs; fix it with: gh api -X PUT repos/<owner>/<repo>/environments/autowriter-tick -F wait_timer=<m>` (`site/scripts/pr-github.mjs:186`), and no successor starts. No timer or no environment gives `The environment autowriter-tick has no wait timer rule; fix it with: ...` (`site/scripts/pr-github.mjs:184`). The chain ends and nothing restarts it (`site/.agents/skills/watch-an-unattended-pull-request.md:74-76`). The pull request stays open and no issue is raised.
  **Needs:** P1, P2

### Phase 6. Who is told, and when

#### P13. Where urgent alerts go

**Ask:** Where should urgent alerts go: to a Slack channel, to another chat tool, or only to GitHub issues?
**Cannot be derived because:** only you know which tool you read every day.
**Options:**

- **A. A Slack incoming webhook, as built:** `spend-ceiling`, `credential` and `no-convergence` escalations post to Slack and open an issue. `hard-stop` and `unrepairable` open an issue only (`site/scripts/autowriter-ledger.mjs:15-16` and `:26-29`). Cost: a Slack workspace and a webhook to create. Anyone with the URL can post. The skill says the last two kinds "wait for the morning digest" (`site/.agents/skills/guard-the-unattended-writer.md:45-46`), and no workflow in `.github/workflows/` builds a digest [INFERENCE], so only GitHub's issue notice tells you.
- **B. Another chat tool with a Slack-compatible incoming webhook:** the sender posts `{ text: ... }` as JSON to the URL (`site/scripts/escalate-channels.mjs:107-112`) and accepts any status from 200 to 299 (`:115`). Cost: untested against other products [INFERENCE].
- **C. GitHub issues only:** needs an engine change. `requiredChannels` returns `['issue']` for every kind (`site/scripts/autowriter-ledger.mjs:26-29`), the readiness test drops `SLACK_WEBHOOK_URL` (`.github/workflows/write-daily.yml:39`), and the Slack bindings go. Cost: urgent alerts arrive as issue emails, and only if you watch the repository (P14). The tests that pin the Slack rule fail until you edit them [INFERENCE].
- **Recommended:** A, because it is the only channel the engine ships and tests, unless you do not use Slack. Then B. Choose C only if you will read the repository's issues every day.
  **Lands in:** repository secret `SLACK_WEBHOOK_URL`. Store it as a secret, because six workflow bindings and the readiness test read `secrets.SLACK_WEBHOOK_URL` (`.github/workflows/write-daily.yml:39`, `:86`, `:137`, `:229`, `:254`; `.github/workflows/watch-pr.yml:60`, `:150`). For C also `site/scripts/autowriter-ledger.mjs:26-29` and `.github/workflows/write-daily.yml:39`.
  **If wrong:** A missing or wrong webhook stops the run at readiness, green (`.github/workflows/write-daily.yml:39`). At escalation time the receipt reads `SLACK_WEBHOOK_URL is not set; create the repository secret of that name` (`site/scripts/escalate-channels.mjs:9`), the command exits 1, and `npm run gate:autowriter` stays red with `escalation-undelivered` until `redeliver` succeeds (`site/scripts/autowriter-gate.mjs:51`). A webhook stored as a variable is read as empty, because the bindings read `secrets.` [INFERENCE: derived from `.github/workflows/write-daily.yml:39`].
  **Needs:** P1

#### P14. Who reads the alerts and the failed-run emails

**Ask:** Which person reads the escalation issues and the failed-run emails, and will that person watch the repository for issues and for Actions failures?
**Cannot be derived because:** notification routing is a personal GitHub setting that the repository cannot read.
**Options:**

- **A. You watch the repository, and the bot account's mail is forwarded to you:** Cost: more email. Escalation issues come from the workflow's own token, so only people who watch the repository see them [INFERENCE]. Failed Watch PR runs email the account that started them, which is the bot [INFERENCE].
- **B. The token belongs to your own account (P3 option B):** the emails reach you with no forwarding. Cost: they carry your name and mix with your own runs.
- **C. Slack only:** you rely on P13 and an occasional look at the Actions tab. Cost: a dead Watch PR chain and an expired token raise no Slack message, so they stay unseen.
- **Recommended:** A, because it covers both the issue channel and the silent chain-death path, unless P3 chose B. Then B.
  **Lands in:** your GitHub notification settings, the repository's Watch menu, and the bot account's mail forwarding. No engine file changes.
  **If wrong:** An `unrepairable` or `hard-stop` escalation sits as an unread issue. A dead Watch PR chain shows only as a red run in the bot's mailbox (`site/.agents/skills/watch-an-unattended-pull-request.md:74-76`). An expired token raises no issue and no Slack message (P4). Articles stall and nothing tells you [INFERENCE].
  **Needs:** P3, P13

#### P15. When the daily run starts

**Ask:** At what hour in UTC should the daily run start, and which person edits that schedule last?
**Cannot be derived because:** it depends on when you read pull requests and which timezone you work in. The shipped line carries one site's choice, and its comment names that site's local time (`.github/workflows/write-daily.yml:7-8`).
**Options:**

- **A. Keep the shipped time:** Cost: it may not suit your day, and the comment at `.github/workflows/write-daily.yml:7` names another site's timezone.
- **B. Pick a time that puts the merge in your working hours:** a merge cannot happen before the pull request is `loop.quarantineHours` old. So the earliest merge is the start time, plus the run time, plus the quarantine, plus up to one tick. Keep the minute off the top of the hour, because scheduled runs queue there (`.github/workflows/write-daily.yml:7`).
- **C. Dispatch only:** delete `schedule` and keep `workflow_dispatch` (`.github/workflows/write-daily.yml:9`). Cost: a person starts every run, so nothing is unattended.
- **Recommended:** B, because the quarantine fixes when a merge can happen and you can plan the day you read the pull request, unless you want the loop to run unnoticed. Then A.
  **Lands in:** `.github/workflows/write-daily.yml`, key `on.schedule[0].cron`, in UTC.
  **If wrong:** Nothing breaks. The timing is only off. GitHub disables scheduled workflows of a public repository after 60 days without repository activity [INFERENCE: GitHub documentation, not read in full]. Failed scheduled runs email the user who created the workflow, or the user who last changed the cron line (https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs). Keep yourself, not the bot, as the last editor.
  **Needs:** P1, P14
