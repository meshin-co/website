### 2.1 What published reference architectures name, and where they agree

The searches behind this record did not turn up a reference architecture for multi-agent systems from a standards body. I did not browse the ISO, IEC or IEEE catalogues, so read that as "not found", not "does not exist". NIST has a standards initiative and no finished agent guidance (2.4). What exists comes from three clouds (Microsoft, Google, AWS), two AI labs (Anthropic, OpenAI) and one foundation checklist (CNCF). All of it is vendor or foundation guidance. None of it is measured data.

- **Microsoft (Multi-agent Reference Architecture site), page last updated 2025-08-18 (primary).** [S1](https://microsoft.github.io/multi-agent-reference-architecture/docs/reference-architecture/Reference-Architecture.html) The most component-level of the set. It names an orchestrator, a classifier, a registry, a supervisor agent, local and remote agents, an MCP server for tools, knowledge bases and vector databases, and a storage layer for state. “At its core, the Orchestrator (e.g., Semantic Kernel) coordinates agent interactions, consults a classifier for intent routing, and uses a registry for agent discovery and lifecycle management.” “A specialized agent responsible for coordinating the activities of other agents to solve complex tasks.” “Local agents run within the same environment as the orchestrator” “Remote agents operate across network boundaries” “Integration with external tools is supported through an MCP (Model Context Protocol) server.” “The system integrates with knowledge bases and vector databases, and maintains context and state through a persistent storage layer.” Weak point: the page is over a year old (2025-08-18), and it is a guide on a GitHub Pages site under Microsoft's `microsoft` organisation, not a product document. Its security chapter, [S2](https://microsoft.github.io/multi-agent-reference-architecture/docs/security/Security.html) (last updated 2025-05-12), adds: “MCP server validates tool access policies before invocation.” “Every orchestration and agent call is logged with metadata: timestamp, caller identity, input hash, output hash.” “Include manual override mechanisms (e.g., pause/disable an agent class) without affecting the overall system.”
- **Microsoft (Azure Architecture Center), page last updated 2026-02-12 (primary).** [S3](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns) Five orchestration patterns: sequential, concurrent, group chat, handoff and magentic. “The sequential orchestration pattern chains AI agents in a predefined, linear order.” “The handoff orchestration pattern enables dynamic delegation of tasks between specialized agents.” “The magentic orchestration pattern is designed for open-ended and complex problems that don't have a predetermined plan of approach.” On how many agents to use: “Use the lowest level of complexity that reliably meets your requirements.” Vendor guidance with no measured data.
- **Google Cloud (Cloud Architecture Center), page last reviewed 2026-05-28 (primary).** [S4](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system) A single-agent system, plus multi-agent sequential, parallel, loop and coordinator patterns. “If you're early in your agent development, we recommend that you start with a single agent.” “If your workload is predictable or highly structured, or if it can be executed with a single call to an AI model, it can be more cost effective to explore non-agentic solutions for your task.” “The multi-agent loop agent pattern repeatedly executes a sequence of specialized subagents until a specific termination condition is met.” “The multi-agent coordinator pattern uses a central agent, the coordinator, to direct a workflow.” Vendor guidance with no measured data.
- **Google Cloud (Cloud Architecture Center), page last reviewed 2025-09-16 (primary).** [S5](https://docs.cloud.google.com/architecture/multiagent-ai-system) A reference architecture with a coordinator agent, A2A between agents and MCP to tools. “A coordinator agent controls the agentic AI system in this example.” “The agents can communicate with each other by using the Agent2Agent (A2A) protocol, which enables interoperability between agents regardless of their programming language and runtime.” “The Model Context Protocol (MCP) facilitates access to tools by standardizing the interaction between agents and tools.” “AI agents can be deployed as serverless Cloud Run services, as containerized apps on Google Kubernetes Engine (GKE), or on Agent Runtime on Gemini Enterprise Agent Platform.” Weak point: the review date is 2025-09-16, yet the text names “Agent Runtime on Gemini Enterprise Agent Platform”, and I could not date those product names. If they are newer than the review date, the page was edited without a new review date. Check product names before citing them as current.
- **AWS (Well-Architected Framework), publication date 2026-06-10 (primary).** [S6](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html) A Well-Architected lens for agents. This is the landing page. It lists best-practice codes that link to child pages, and I read only some of the child pages. “Multi-agent systems introduce coordination overhead, handoff complexity, and distributed failure modes.” “Bounded autonomy: Every agent operates within explicitly defined scope boundaries, with guardrails that constrain behavior regardless of inputs received” “Tiered oversight models match the level of human review to the risk and reversibility of each agent action, preserving human judgment where it matters most” “AGENTOPS05: Implement tracing, anomaly detection, and operational dashboards” “AGENTOPS06: Establish testing and evaluation frameworks with LLM-as-judge” One child page, [S7](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel02-bp05.html), sorts agent actions into approval tiers: “You have agent actions classified into tiers (autonomous, notify, and approve) based on impact and reversibility.”
- **AWS Marketplace (AI agent learning series, Module 4), undated (primary).** [S8](https://aws.amazon.com/marketplace/build-learn/ai-agent-learning-series/multi-agent-architectures) “Four planes make up every production multi-agent system, regardless of orchestration pattern: the control plane, the execution plane, the state plane, and the capability plane.” “I’d recommend starting with the simplest pattern that fits your workflow and only moving to a more complex one when you hit a concrete limitation.” Weak point: undated, written in the first person, and part of a Marketplace learning series that recommends partner products by name. Use it for the "four planes" wording only if you attribute it. Strategy-level trust guidance from [S9](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-operationalizing-agentic-ai/focus-areas-trust.html) (undated): “Each agent must operate with a verifiable identity, scoped permissions, and traceable execution history.”
- **CNCF (AI Technical Community Group blog post), 2026-03-23 (primary).** [S10](https://www.cncf.io/blog/2026/03/23/cloud-native-agentic-standards/) A checklist, not a reference architecture with named components. It says of itself that it “is not intended to be exhaustive”. “This paper explores four key areas where standardization is needed to ensure interoperability, security, and observability from the outset.” “Considerations should be taken in terms of only applying narrowly scoped MCP server tooling access for the given tools required, for both security and optimal system performance reasons.” “Analyze the entire sequence of steps taken by an agent in relation to an expected optimal path.” “Each agent should have a unique, verifiable identity to support traceability, accountability, and secure communication across system boundaries.”
- **Anthropic (Engineering), 2024-12-19, page updated 2026-08-10 (primary).** [S11](https://www.anthropic.com/engineering/building-effective-agents) The clearest definitions, and still widely cited. “Workflows are systems where LLMs and tools are orchestrated through predefined code paths.” “Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.” “In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results.” “When building applications with LLMs, we recommend finding the simplest solution possible, and only increasing complexity when needed.” Weak point: the page now carries a note: “Much of the tooling landscape described in this post has changed since December 2024.” It points readers to Anthropic's Managed Agents material instead.
- **Anthropic (Engineering), 2025-06-13, page modified 2026-01-06 (primary).** [S12](https://www.anthropic.com/engineering/multi-agent-research-system) A production multi-agent system described by its maker. “Our Research system uses a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel.” Weak point: one vendor's own system on a read-heavy research task, and the results come from its own evaluations: “Our internal evaluations show that multi-agent research systems excel especially for breadth-first queries” Later, **Anthropic (Engineering), 2026-04-08 (primary).** [S13](https://www.anthropic.com/engineering/managed-agents) describes a design that separates the model loop ("the brain") from its tools ("the hands") and keeps the session log outside the loop: “Because the session log sits outside the harness, nothing in the harness needs to survive a crash.” “That interface supports any custom tool, any MCP server, and our own tools.” A vendor blog about its own product.
- **OpenAI, April 2025 (PDF undated; served with Last-Modified 2025-04-11) (primary).** [S14](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) Dated April 2025, about 18 months before this record. A vendor guide with no measured results. “Single-agent systems, where a single model equipped with appropriate tools and instructions executes workflows in a loop” “Multi-agent systems, where workflow execution is distributed across multiple coordinated agents” “coordinates multiple specialized agents via tool calls, each handling a specific task or domain.” “This pattern involves using many agents on equal footing, where one agent can directly hand off control of the workflow to another agent.” On tools: “Assess the risk of each tool available to your agent by assigning a rating—low, medium, or high—based on factors like read-only vs. write access, reversibility, required account permissions, and financial impact.”

**Where the publishers agree.** `[INFERENCE]` Eight points recur across at least three independent publishers. Each citation below points to a source whose quote or page text supports it.

1. Start with one agent and add more only for a reason. Microsoft ([S3](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)), Google ([S4](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system)), Anthropic ([S11](https://www.anthropic.com/engineering/building-effective-agents)) and the AWS module ([S8](https://aws.amazon.com/marketplace/build-learn/ai-agent-learning-series/multi-agent-architectures)) say it in so many words.
2. In the multi-agent form, one component coordinates the others. It is called orchestrator in [S1](https://microsoft.github.io/multi-agent-reference-architecture/docs/reference-architecture/Reference-Architecture.html), supervisor in the same page, coordinator in [S5](https://docs.cloud.google.com/architecture/multiagent-ai-system) and lead agent in [S12](https://www.anthropic.com/engineering/multi-agent-research-system). The names differ; the role does not (see 3.2).
3. Tools sit behind a protocol boundary, usually MCP: [S1](https://microsoft.github.io/multi-agent-reference-architecture/docs/reference-architecture/Reference-Architecture.html), [S5](https://docs.cloud.google.com/architecture/multiagent-ai-system), [S10](https://www.cncf.io/blog/2026/03/23/cloud-native-agentic-standards/), [S13](https://www.anthropic.com/engineering/managed-agents) and [S15](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec06.html).
4. State lives outside the model's context window: a storage layer ([S1](https://microsoft.github.io/multi-agent-reference-architecture/docs/reference-architecture/Reference-Architecture.html)), a session log ([S13](https://www.anthropic.com/engineering/managed-agents)), agent memory ([S16](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/build-secure-process)), a plan saved to memory ([S12](https://www.anthropic.com/engineering/multi-agent-research-system)) and memory in the infrastructure layer of the AWS lens ([S6](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html)).
5. Every step is logged or traced, and observability is designed in from the start: [S2](https://microsoft.github.io/multi-agent-reference-architecture/docs/security/Security.html), [S16](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/build-secure-process) and [S17](https://microsoft.github.io/multi-agent-reference-architecture/docs/observability/Observability.html) (Microsoft), [S15](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec06.html) (AWS) and [S10](https://www.cncf.io/blog/2026/03/23/cloud-native-agentic-standards/) (CNCF).
6. Evaluation covers the steps taken, not only the final answer: [S10](https://www.cncf.io/blog/2026/03/23/cloud-native-agentic-standards/), [S18](https://microsoft.github.io/multi-agent-reference-architecture/docs/evaluation/Evaluation.html) and [S19](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
7. High-impact actions need a person's approval, in tiers: [S7](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel02-bp05.html), [S2](https://microsoft.github.io/multi-agent-reference-architecture/docs/security/Security.html), [S16](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/build-secure-process) and [S20](https://modelcontextprotocol.io/specification/2026-07-28/server/tools). Section 3.3 says how well this works.
8. Each agent has its own identity and scoped permissions: [S10](https://www.cncf.io/blog/2026/03/23/cloud-native-agentic-standards/), [S9](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-operationalizing-agentic-ai/focus-areas-trust.html), [S21](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization) and [S16](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/build-secure-process).

### 2.2 Five failure modes, each with a dated source

These are the ways multi-agent systems fail in the sources I read. For each one I give the evidence and say how strong it is in the same sentence.

**F1. The agents disagree, forget the task, or do not check each other's work.**

- **Cemri et al. (arXiv 2503.13657, NeurIPS 2025 Datasets and Benchmarks), v1 2025-03-17, v3 2025-10-26 (primary).** [S22](https://arxiv.org/pdf/2503.13657) A research paper that studied traces of multi-agent systems. “reveals 41% to 86.7% failure rate on 7 state-of-the-art (SOTA) open-source MAS” The authors sort the failures into three groups: “System Design Issues (41.8%) Inter-Agent Misalignment (36.9%) Task Verification (21.3%)” Among the listed modes, three bear on loops and state: “step repetitions (FM-1.3, 15.7%), context loss (FM-1.4, 2.80%), or not recognizing task completion (FM-1.5, 12.4%)” The counts rest on “The percentages shown represent the prevalence of each failure mode and category as observed in our analysis of 1642 MAS execution traces.” Strength: a peer-reviewed paper (NeurIPS 2025 Datasets and Benchmarks track). The systems studied are seven open-source frameworks, so the rates describe those frameworks. `[INFERENCE]` They do not describe a production system that has an eval gate and a named owner. The authors add: “MAS failure is not merely a function of challenges in the underlying model; a well-designed MAS can result in performance gain when using the same underlying model.”
- **Microsoft (Security blog, AI Red Team), 2026-06-04 (primary).** [S23](https://www.microsoft.com/en-us/security/blog/2026/06/04/updating-taxonomy-failure-modes-agentic-ai-systems-year-red-teaming-taught-us/) Microsoft's AI Red Team updated its failure-mode taxonomy. “The update adds seven new failure mode categories, expands the mitigations section, and grounds the framework in 12 months of red team engagements against deployed agentic systems.” “Multi-agent architectures involve delegation chains where orchestrators pass tasks to other agents.” Strength: a vendor security team's own taxonomy; the quotes come from the blog post, not from the full taxonomy document.

**F2. More agents can make the result worse, and errors can multiply.**

- **Google Research (blog), 2026-01-28 (primary).** [S24](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/) Google Research tested single-agent and multi-agent set-ups. “Through a controlled evaluation of 180 agent configurations, we derive the first quantitative scaling principles for AI agent systems” “We found that independent multi-agent systems (agents working in parallel without talking) amplified errors by 17.2x.” “Centralized systems (with an orchestrator) contained this amplification to just 4.4x.” “on tasks requiring strict sequential reasoning (like planning in PlanCraft), every multi-agent variant we tested degraded performance by 39-70%.” The paper behind it is **Kim et al., Google Research (arXiv 2512.08296), v1 2025-12-09, v3 2026-04-08 (primary).** [S25](https://arxiv.org/abs/2512.08296) “Across 260 configurations spanning six agentic benchmarks, five canonical architectures (Single-Agent and four Multi-Agent: Independent, Centralized, Decentralized, Hybrid), and three LLM families, we perform controlled evaluations” “Relative performance change compared to single-agent baseline ranges from +80.8% on decomposable financial reasoning to -70.0% on sequential planning” Strength: one study on benchmarks. The blog says 180 configurations and the version-3 abstract says 260, so the paper changed after the blog. Quote one version and name it.
- [S12](https://www.anthropic.com/engineering/multi-agent-research-system) puts a price on it: “In our data, agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats.” It also says “Multi-agent systems work mainly because they help spend enough tokens to solve the problem.” and “One step failing can cause agents to explore entirely different trajectories, leading to unpredictable outcomes.”.

**F3. A loop does not end, or the cost runs away.**

- **Hou et al. (arXiv 2607.01641), 2026-07-02 (primary).** [S26](https://arxiv.org/abs/2607.01641) A static-analysis study of agent code. “Such failures can amplify a single request into long running model and tool execution, causing cost exhaustion, model denial of service, context growth, and repeated external side effects.” “We evaluate IAL-Scan on 6,549 LLM agent repositories. It reports 74 potential findings, among which manual review confirms 68 IAL failures across 47 projects, achieving 91.9% precision.” Strength: one preprint, posted 2026-07-02, from the team that built the scanner. It counts code patterns in public repositories. It does not show a loop that ran in production.
- MAST, above, counts “step repetitions (FM-1.3, 15.7%)” and “not recognizing task completion (FM-1.5, 12.4%)” among its failure modes.
- [S12](https://www.anthropic.com/engineering/multi-agent-research-system) describes its own early prototypes: “Early agents made errors like spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates.” and says it responded by “setting explicit guardrails to prevent the agents from spiraling out of control”. This is a vendor's account of its own early work, with no date for the incidents.
- Forecasts, not measurements. **Gartner (press release), 2025-06-25 (primary).** [S27](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027) “Over 40% of agentic AI projects will be canceled by the end of 2027, due to escalating costs, unclear business value or inadequate risk controls, according to Gartner, Inc.” The release leans on “According to a January 2025 Gartner poll of 3,412 webinar attendees, 19% said their organization had made significant investments in agentic AI”. **Gartner (press release), 2026-08-17 (date in the URL) (primary).** [S28](https://www.gartner.com/en/newsroom/press-releases/2026-08-17-gartner-predicts-ai-inference-costs-per-agentic-workflow-will-increase-more-than-fivefold-through-2028) “AI inference costs per agentic workflow will increase more than fivefold through 2028 according to Gartner, Inc.” Both are predictions by an analyst firm. I did not read the reports behind them.
- Not found: a dated, checkable post-mortem of a production agent loop that ran away and cost real money. The only items I found were blog posts that repeat one set of figures with no primary record. Treat any story of the form "an agent burned $X overnight" as unsourced until its record is found.

**F4. The context window fills, drifts, or is lost.**

- **Chroma (technical report), 2025-07-14 (primary).** [S29](https://www.trychroma.com/research/context-rot) “In this report, we evaluate 18 LLMs, including the state-of-the-art GPT-4.1, Claude 4, Gemini 2.5, and Qwen3 models.” “Our results reveal that models do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows.” Weak point: Chroma sells a vector database, which gains if retrieval beats long context. Its tasks are deliberately simple (“Each task remains intentionally simple and is deliberately controlled to isolate the impact of context length alone.”), and the models are the 2025 generation.
- **Anthropic (Engineering), 2025-09-29 (primary).** [S30](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) “Context, therefore, must be treated as a finite resource with diminishing marginal returns.” “overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later.” “Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens).”
- In a multi-agent set-up the problem has a second side. **Cognition, 2025-06-12 (primary).** [S31](https://cognition.com/blog/dont-build-multi-agents) “Share context, and share full agent traces, not just individual messages” “Actions carry implicit decisions, and conflicting decisions carry bad results” Cognition sells a coding agent, Devin, and the post is an argument, not a measurement.
- [S12](https://www.anthropic.com/engineering/multi-agent-research-system) reports saving state because of a limit: “saving its plan to Memory to persist the context, since if the context window exceeds 200,000 tokens it will be truncated and it is important to retain the plan”

**F5. A hijacked or over-privileged agent acts with real authority.**

- **Meta (AI blog), 2025-10-31 (primary).** [S32](https://ai.meta.com/blog/practical-ai-agent-security/) “Prompt injection is a fundamental, unsolved weakness in all LLMs.” The rule: “agents must satisfy no more than two of the following three properties within a session to avoid the highest impact consequences of prompt injection.” The three: “An agent can process untrustworthy inputs”; “An agent can have access to sensitive systems or private data”; “An agent can change state or communicate externally”. If all three are present, “then the agent should not be permitted to operate autonomously and at a minimum requires supervision”. Meta adds: “Designs that satisfy the Agents Rule of Two can still be prone to failure” Strength: a design rule of thumb from one company's security team, not a standard.
- **NIST (CAISI technical blog), 2025-01-17, updated 2025-12-19 (primary).** [S33](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations) “Currently, many AI agents are vulnerable to agent hijacking, a type of indirect prompt injection in which an attacker inserts malicious instructions into data that may be ingested by an AI agent, causing it to take unintended, harmful actions.” “This resulted in an increase in attack success rate from 11% for the strongest baseline attack to 81% for the strongest new attack.” “The average success rate across these five injection tasks is 57%.” Strength: a government lab's tests on a public benchmark. The post is from January 2025 and was updated in December 2025, so the models it tested are not today's.
- **OWASP GenAI Security Project (Agentic Security Initiative), December 2025, launch announced 2025-12-09 (primary).** [S34](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) The OWASP Top 10 for Agentic Applications names ten risks: ASI01: Agent Goal Hijack; ASI02: Tool Misuse and Exploitation; ASI03: Identity and Privilege Abuse; ASI04: Agentic Supply Chain Vulnerabilities; ASI05: Unexpected Code Execution (RCE); ASI06: Memory & Context Poisoning; ASI07: Insecure Inter-Agent Communication; ASI08: Cascading Failures; ASI09: Human-Agent Trust Exploitation; ASI10: Rogue Agents. It names risks; I did not check how the ranking was built. **OWASP GenAI Security Project, resource page dated 2026-08-03 (primary).** [S35](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/) “Excessive Agency climbed to third, the most consequential move on the list, because the vote and the record agree that agentic deployments are where the damage is landing.” “Within the context of agentic systems, Excessive Agency can manifest as ASI02: Tool Misuse & Exploitation, ASI03: Identity & Privilege Abuse and ASI08: Cascading Failures.”
- The approval step is itself a point of failure. **Anthropic (Engineering), 2026-05-25 (primary).** [S36](https://www.anthropic.com/engineering/how-we-contain-claude) “Our telemetry showed users approved roughly 93% of permission prompts.” “The more approvals a user sees, the less attention they pay to each, becoming over time much less diligent in their supervision.” “Design for containment at the environment layer first, then steer behavior at the model layer.” Strength: the vendor's own telemetry from its own product, with no method given. The Microsoft taxonomy ([S23](https://www.microsoft.com/en-us/security/blog/2026/06/04/updating-taxonomy-failure-modes-agentic-ai-systems-year-red-teaming-taught-us/)) says “HitL bypass was the most consistently exploited failure mode, at very high frequency.”
- One reported incident. **AI Incident Database (Responsible AI Collaborative), undated; the entry gives the incident date 2025-07-18 (secondary).** [S37](https://incidentdatabase.ai/cite/1152/) “An AI-powered development assistant on Replit's platform reportedly deleted a live production database during an active code freeze, despite receiving repeated instructions not to make changes.” The press account (**The Register, 2025-07-21 (secondary).** [S38](https://www.theregister.com/software/2025/07/21/vibe-coding-service-replit-deleted-production-database/719783)): “The founder of SaaS business development outfit SaaStr has claimed AI coding tool Replit deleted a database despite his instructions not to change any code without permission.” Replit's own post of the same day (**Replit (blog), 2025-07-21 (primary).** [S39](https://replit.com/blog/introducing-a-safer-way-to-vibe-code-with-replit-databases)) describes a product change: “Until now, Replit apps used a single database for both development and live customer data, making it challenging to safely test and deploy updates.” Strength: weak. What the agent did comes from the customer's claim. This was a coding assistant, and the sources I read do not say whether more than one agent was involved. Use it, if at all, as a reported case of too much access, not as multi-agent evidence.

### 2.3 What production needs that a demo does not

Eight things. For each one: what the sources say, who says it, and how strong it is.

**1. Hard limits on steps and on spend.**

- OpenAI Agents SDK. **OpenAI (Agents SDK source on GitHub, main branch), undated, read 2026-10-02 (primary).** [S40](https://raw.githubusercontent.com/openai/openai-agents-python/main/src/agents/run_config.py) “DEFAULT_MAX_TURNS = 10” The docs (**OpenAI (Agents SDK docs), undated living page, read 2026-10-02 (primary).** [S41](https://openai.github.io/openai-agents-python/running_agents/)) say: “If we exceed the max_turns passed, we raise a MaxTurnsExceeded exception. Pass max_turns=None to disable this turn limit.”
- LangGraph. **LangChain (LangGraph docs), undated living page, read 2026-10-02 (primary).** [S42](https://docs.langchain.com/oss/python/langgraph/graph-api) “Starting in version 1.0.6, the default recursion limit is set to 1000 steps.”
- Microsoft Agent Framework. **Microsoft (Agent Framework API reference), page metadata updated 2025-12-19, read 2026-10-02 (primary).** [S43](https://learn.microsoft.com/en-us/python/api/agent-framework-core/agent_framework.workflow?view=agent-framework-python-latest) “The maximum number of iterations the workflow will run for convergence.” “Default value: 100”
- Google ADK. **Google (Agent Development Kit docs), undated living page, read 2026-10-02 (primary).** [S44](https://google.github.io/adk-docs/agents/workflow-agents/loop-agents/) “Crucially, the LoopAgent itself does not inherently decide when to stop looping. You must implement a termination mechanism to prevent infinite loops.” “Set a maximum number of iterations in the LoopAgent.”
- Claude Agent SDK. **Anthropic (Claude Agent SDK docs), undated living page, read 2026-10-02 (primary).** [S45](https://platform.claude.com/docs/en/agent-sdk/agent-loop) “Without limits, the loop runs until Claude finishes on its own, which is fine for well-scoped tasks but can run long on open-ended prompts” “Setting a budget is a good default for production agents.” “The budget cap covers subagents: their spend counts toward the total.”
- `[INFERENCE]` The defaults I found are 10 turns (OpenAI), 100 iterations (Microsoft) and 1000 steps (LangGraph). They are different units, and each number is ten times the one before. The Claude page describes a loop that runs until it finishes unless a limit is set. A limit that suits one framework does not carry over to another. The owner should state the limit in the unit the system uses (section 5, question 6). All five are vendors documenting their own software, and the pages are living pages.
- Spend caps outside the framework. **LiteLLM (docs), page updated 2026-10-01, read 2026-10-02 (primary).** [S46](https://docs.litellm.ai/docs/proxy/users) “Agent budgets: Set rate limits (tpm/rpm) and session-level caps (iterations, dollar budget) on agents” OWASP says: “Effective defense demands token-aware cost controls, hard spending caps, agent-level circuit breakers” Microsoft's Cloud Adoption Framework: **Microsoft (Cloud Adoption Framework), page last updated 2026-06-26 (primary).** [S21](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization) “Set up real-time alerts to notify teams when spending approaches budget thresholds.” and, in [S16](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/build-secure-process), “Enforce quota and cost governance.”
- How spend is counted. **AWS (Well-Architected Agentic AI Lens), lens published 2026-06-10, page itself undated (primary).** [S47](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost05.html) “Agent spending is attributable at the reasoning-cycle, agent, workflow, and tenant level rather than only at the account level.” “Orchestration overhead and worker execution costs are separable, so teams can tell where each dollar is spent.” `/approach` promises "cost per outcome". That is a different measure from spend per reasoning cycle or per agent. The site defines its own measure at `/faq/how-is-cost-per-outcome-measured`. Link there; do not restate it.

The Temporal and OpenAI Agents SDK integration (**Temporal (blog), 2025-07-30, GA note 2026-03-23 (primary).** [S50](https://temporal.io/blog/announcing-openai-agents-sdk-integration)) carries this note: “Update: As of March 23rd, 2026, the integration between the OpenAI Agents SDK and Temporal's Python SDK is now Generally Available.”
- **Pydantic (Pydantic AI docs), undated living page, read 2026-10-02 (primary).** [S51](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/) “A durable engine keeps one run alive across crashes and restarts.” “Pydantic AI supports eight durable execution solutions, plus a builder for any other engine.”
- **LangChain (LangGraph docs), undated living page, read 2026-10-02 (primary).** [S52](https://docs.langchain.com/oss/python/langgraph/persistence) “When the process restarts, all checkpoints are lost.” The interrupts page (**LangChain (LangGraph docs), undated living page, read 2026-10-02 (primary).** [S53](https://docs.langchain.com/oss/python/langgraph/interrupts)) says: “A checkpointer to persist the graph state (use a durable checkpointer in production)”

- **OpenAI (Agents SDK docs), undated living page, read 2026-10-02 (primary).** [S57](https://openai.github.io/openai-agents-python/tracing/) “Tracing is enabled by default. **4. Evals that run before a change ships.**

- In CI. I searched nine of these pages for "CI". Only [S16](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/build-secure-process) puts evaluations in the pipeline: “Integrate evaluations into CI/CD pipelines to catch issues before production deployment.” That makes "evals in CI" a practice with one primary source among those I read, not a standard.
- What to test in a multi-agent system. **Microsoft (Multi-agent Reference Architecture site), page last updated 2025-10-21 (primary).** [S18](https://microsoft.github.io/multi-agent-reference-architecture/docs/evaluation/Evaluation.html) “Validate correct function/tool calling and API interactions” “Validate recovery mechanisms for failed operations” “Assess efficiency of generated execution plans”
- A judge kept apart from the worker. **Anthropic (Engineering), 2026-03-24 (primary).** [S59](https://www.anthropic.com/engineering/harness-design-long-running-apps) “Separating the agent doing the work from the agent judging it proves to be a strong lever to address this issue.” Weak point: a few example builds, and the same post notes “The harness was over 20x more expensive, but the difference in output quality was immediately apparent.”

### 2.4 Protocols, standards and law the article must stay consistent with

- **MCP.** [S62](https://modelcontextprotocol.io/specification/2026-07-28) is revision 2026-07-28. “Tools represent arbitrary code execution and must be treated with appropriate caution.” “While MCP itself cannot enforce these security principles at the protocol level” The changelog (**Model Context Protocol project, revision 2026-07-28 (primary).** [S70](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) lists “Deprecate the Roots, Sampling, and Logging features” Governance: **Model Context Protocol project (blog), 2025-12-09, updated 2026-03-12 (primary).** [S71](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/) “Anthropic is donating MCP to the Agentic AI Foundation, a directed fund under the Linux Foundation.” The foundation's own press release (**The Linux Foundation (press release), 2025-12-09 (primary).** [S72](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)) says “MCP has rapidly become the universal standard protocol for connecting AI models to tools, data and applications, with more than 10,000 published MCP servers” Weak point: a foundation describing its own project. - **A2A.** **A2A project (GitHub release), 2026-03-12 (primary).** [S73](https://github.com/a2aproject/A2A/releases/tag/v1.0.0) “1.0.0 (2026-03-12)” **Agentic AI Foundation (blog), 2026-08-17 (primary).** [S74](https://aaif.io/blog/a2a-joins-aaif) “Agent2Agent (A2A), the open standard for inter-agent communication, is joining the Agentic AI Foundation (AAIF) as a hosted project.” “A2A v1.0, the first stable specification, shipped in March 2026.” The project's own page (**A2A project (a2a-protocol.org), undated home page, read 2026-10-02 (primary).** [S75](https://a2a-protocol.org/)) says “MCP is for agent-to-tool communication: it standardizes how an agent connects to its tools, APIs, and resources to get information.” and “Not a sub-agent or tool-call protocol.” Strength: all three are the project's own statements. - **EU AI Act.** **European Commission (Shaping Europe's digital future), 2026-07-27, updated 2026-07-31 (primary).** [S78](https://digital-strategy.ec.europa.eu/en/news/ai-omnibus-enters-force) “On 27 July 2026, the AI Omnibus enters into force across the EU, bringing extended timelines to administrative simplification.” “High-risk AI systems in Annex III: Rules apply starting 2 December 2027” “High-risk AI embedded in physical products (machinery, toys, lifts, etc.) in Annex I: Rules apply starting 2 August 2028” The regulation itself (**European Union (Official Journal, via EUR-Lex), 2026-07-08 (date of signature) (primary).** [S79](https://eur-lex.europa.eu/eli/reg/2026/1744/oj)): “2 December 2027 as regards AI systems classified as high-risk pursuant to Article 6(2) and Annex III” “2 August 2028 as regards AI systems classified as high-risk pursuant to Article 6(1) and Annex I” The Commission's service desk still shows the old text of Article 14, with this notice: “This provision has been amended by the Digital Omnibus on AI. ## 3. What is contested or unsettled

Twelve points. For each one: who says what, how strong it is, and what the page can safely say. A page that states one of these as fact will age badly.

**3.1 One agent or many.**

- For many, on the right task. [S12](https://www.anthropic.com/engineering/multi-agent-research-system) says “multi-agent systems excel at valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools.” It prices the choice: “For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance.”
- Against, for parallel writers. [S31](https://cognition.com/blog/dont-build-multi-agents) (2025-06-12): “it is evident that in 2025, running multiple agents in collaboration only results in fragile systems.” Its advice: “The simplest way to follow the principles is to just use a single-threaded linear agent:” Ten months later, **Cognition, 2026-04-22 (primary).** [S80](https://cognition.com/blog/multi-agents-working) says “multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions.” and “Our original observations still hold today for parallel-writer swarms” The same post gives two rules that pull apart: “Share as much context as possible between the agents.” and, for review agents, “Interestingly, we found this technique to work best when the coding and review agents do not share any context beforehand.” Cognition sells its own agent, so this is a product maker's view.
- By task, measured. [S25](https://arxiv.org/abs/2512.08296) reports a range from +80.8% to −70.0% against a single agent, depending on the task (quote in 2.2, F2).
- Commentary. **LangChain (blog), 2025-06-16 (secondary).** [S81](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems) (secondary, from a vendor of agent tooling) says “Despite their opposing titles, I would argue they actually have a lot in common and contain some insights as to how and when to build multi-agent systems:”
- `[INFERENCE]` The publishers agree on "one agent first" and disagree on where the line sits. The line seems to depend on the task: many independent reads versus shared writes. I found no source that settles it for a production workload. I also found none that separates the gain from structure from the gain from extra tokens, which Anthropic hints at in its own sentence about spending enough tokens. The page can state the rule and the cost. It cannot state a universal threshold. The threshold is the owner's (question 5).

**3.2 Which coordination shape is the default, and what to call it.** Microsoft lists five patterns and Google lists a single agent plus four multi-agent patterns (2.1). In Google's study, independent agents contained error worst and centralised ones better: “We found that independent multi-agent systems (agents working in parallel without talking) amplified errors by 17.2x.” “Centralized systems (with an orchestrator) contained this amplification to just 4.4x.” That favours an orchestrator. Cognition favours one linear agent. The coordinator is called orchestrator, supervisor, coordinator, manager agent or lead agent depending on the source. No standard vocabulary exists. The page must pick one word and define it once, on one page (L50, L51, L53), and name the others once.

**3.3 Is a person's approval a safe default?** The protocol says a human SHOULD be in the loop ([S20](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). AWS sorts actions into tiers so that not every action needs one ([S7](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentrel02-bp05.html)). Against that, [S36](https://www.anthropic.com/engineering/how-we-contain-claude) reports “Our telemetry showed users approved roughly 93% of permission prompts.” and [S23](https://www.microsoft.com/en-us/security/blog/2026/06/04/updating-taxonomy-failure-modes-agentic-ai-systems-year-red-teaming-taught-us/) names bypass of the human step as the most exploited failure mode. Both findings are the vendors' own. The page can say approval is a control that can fail, through habit or through bypass, and attribute each finding. It cannot say how many prompts is too many.

**3.4 How far the numbers can be trusted.** The numbers in this field come in five weak forms.

- A vendor's own telemetry or evaluation: the 93% above; [S12](https://www.anthropic.com/engineering/multi-agent-research-system), whose results come from “Our internal evaluations show that multi-agent research systems excel especially for breadth-first queries”.
- A vendor-run survey: [S58](https://www.langchain.com/state-of-agent-engineering), self-selected.
- An analyst forecast: [S27](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027) and [S28](https://www.gartner.com/en/newsroom/press-releases/2026-08-17-gartner-predicts-ai-inference-costs-per-agentic-workflow-will-increase-more-than-fivefold-through-2028). They are predictions, and the 2025 release leans on a poll of webinar attendees.
- A single study that changed: [S25](https://arxiv.org/abs/2512.08296) has three versions (v1 2025-12-09, v3 2026-04-08), and the blog and the abstract give different configuration counts.
- A study of a narrow sample: [S22](https://arxiv.org/pdf/2503.13657) covers seven open-source frameworks, and [S26](https://arxiv.org/abs/2607.01641) is a preprint that counts code patterns.

Rule for the page: put the source and the date next to each number, and never write "industry average".

**3.5 Standards are moving. Pin a date.** Everything below is less than a year old, or has changed within it.

- MCP: the 2026-07-28 revision deprecates Roots, Sampling and Logging ([S70](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Authorization is optional ([S67](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). It joined the Agentic AI Foundation on 2025-12-09.
- A2A: version 1.0.0 on 2026-03-12 ([S73](https://github.com/a2aproject/A2A/releases/tag/v1.0.0)), and it joined the foundation on 2026-08-17 ([S74](https://aaif.io/blog/a2a-joins-aaif)). Its own page says it is “Not a sub-agent or tool-call protocol.” while Google's reference architecture ([S5](https://docs.cloud.google.com/architecture/multiagent-ai-system)) uses it between a coordinator and its agents. Sources disagree on whether A2A belongs inside one system.
- OpenTelemetry: GenAI conventions are "development" ([S55](https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/model/manifest.yaml)).
- NIST: an initiative announced 2026-02-17, still at convenings and gap analyses ([S76](https://www.nist.gov/artificial-intelligence/ai-agent-standards-initiative)).
- OWASP: the agentic Top 10 launched 2025-12-09 ([S34](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)).
- CNCF: a checklist posted 2026-03-23 that calls itself non-exhaustive ([S10](https://www.cncf.io/blog/2026/03/23/cloud-native-agentic-standards/)).
- AWS: a lens published 2026-06-10 ([S6](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentic-ai-lens.html)).

Each claim that names one of these should carry a "checked on" date. I could not confirm whether the core OpenTelemetry traces signal is labelled stable, so the page should not assert it.

**3.6 One named person or a committee.** `/approach` says “One person with the authority to say no, accountable for AI risk, on the org chart.” Microsoft's Cloud Adoption Framework asks for “Assign ownership for agent governance to the same leaders responsible for cloud governance, security, and compliance.” and also for “Designate a human role accountable for approving deployments and monitoring ongoing compliance with ethical standards.” The Microsoft reference architecture asks for a “Establish a cross-functional governance committee”. The EU AI Act asks, for high-risk systems, for “natural persons who have the necessary competence, training and authority”. These do not contradict one person being accountable. They mostly describe a group around that person. The page must say what the one person owns and what they cannot decide alone (question 17).

**3.7 Is a durable-execution engine needed?** Temporal and Pydantic AI, both vendors, say durable execution matters for agent loops ([S49](https://docs.temporal.io/evaluate/why-temporal), [S51](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/)). LangGraph says to use a durable checkpointer ([S53](https://docs.langchain.com/oss/python/langgraph/interrupts)). Anthropic keeps the session log outside the loop ([S13](https://www.anthropic.com/engineering/managed-agents)). I found no source that says every production agent needs a separate engine, and none that measures the benefit. The principle (state survives a crash) is well supported. The product (an engine) is a choice. Appendix B names a "Durable execution" layer, so the owner must say which one is meant (question 3).

**3.8 What "in production" and "rollback" mean.** No outside source I read defines "in production". The site does: “Real users, real transactions, a rollback path, someone on call.” (`/faq/what-counts-as-in-production-for-the-90-day-sprint`). The article should use that bar and link to the FAQ. For rollback, Microsoft says “Always enable immediate rollback to a previous version if anomalies are detected”, Temporal says "instant" (unmeasured), and I found no target time anywhere. One more limit: Anthropic says a model ID does not change, then adds that “Occasionally, infrastructure updates produce minor differences in observable behavior” So rolling back a model ID does not always roll back behaviour.

**3.9 Where "evals in CI" comes from.** Among the pages I searched, one primary source puts evaluations in CI/CD (Microsoft's Cloud Adoption Framework). Anthropic's evals post talks about suites and regression tests, and I did not see it say CI. A claim of "~20 datapoints is enough" appears in a secondary vendor blog ([S81](https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems): “Start small with evals, even ~20 datapoints is enough”). Do not adopt it as a threshold. `/approach` promises "evals in CI", and that rests on practice.

**3.10 Product detail ages in weeks.**

- OpenAI is winding down its hosted Agent Builder and Evals products ([S60](https://openai.com/index/introducing-agentkit/)). The update note is dated 2026-06-03 and the end date in the quote is 2026-11-30.
- Anthropic's effective-agents page says its tooling landscape has changed ([S11](https://www.anthropic.com/engineering/building-effective-agents)).
- Google's multi-agent page was reviewed on 2025-09-16 and names products I could not date ([S5](https://docs.cloud.google.com/architecture/multiagent-ai-system)).
- Anthropic told developers on 2026-09-30 that Claude Sonnet 4.5 will be retired ([S66](https://platform.claude.com/docs/en/about-claude/model-deprecations)).

Name practices. Name products only with a check date.

**3.11 The EU AI Act dates.** The Commission says the Omnibus entered into force on 27 July 2026, with Annex III high-risk rules from 2 December 2027 and Annex I from 2 August 2028 ([S78](https://digital-strategy.ec.europa.eu/en/news/ai-omnibus-enters-force), [S79](https://eur-lex.europa.eu/eli/reg/2026/1744/oj)). The Commission's own service desk still shows the 2024 text of Article 14 and says so ([S64](https://ai-act-service-desk.ec.europa.eu/en/ai-act/article-14)).
